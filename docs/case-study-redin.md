# Case Study: Redin — Field Maintenance Automation

## The Company

**Redin** is a locative maintenance company based in Colombia that operates across 25+ cities. They provide services including painting, electrical work, cleaning, ceiling installation, lighting, waterproofing, plumbing, and general maintenance. Their clients are typically building administrators and property managers.

## The Existing Workflow (Before Automation)

Redin's entire customer-facing operation runs through WhatsApp:

1. **Intake**: A building administrator sends a WhatsApp message describing a maintenance issue — often with photos, voice notes, or videos of the problem
2. **Triage**: An architect (operations person) reads the message, interprets the problem, classifies the type of service and urgency
3. **Coordination**: The architect checks availability, identifies the right technician based on service type and city, and assigns the job
4. **Scheduling**: Back-and-forth via WhatsApp to agree on a date, time, and site access
5. **Tracking**: Work order details are manually entered into their system (AppSheet built on Google Sheets)
6. **Follow-up**: Status updates and completion confirmations via WhatsApp

This loop happens dozens of times per day. The architect is the bottleneck — every new request requires their manual interpretation, classification, and routing.

## The System They Already Have

Redin uses **AppSheet** (Google's no-code platform) backed by **Google Sheets** to manage:
- Client/building database
- Work orders and their statuses
- Technician assignments
- Service history
- Financial tracking (quotes, advances, invoicing)

The owner built this system himself but has zero API knowledge. He couldn't describe his data schema, but he **could share screenshots** of his AppSheet interface — which was enough to reverse-engineer the structure.

## What Was Built

A WhatsApp bot that automates the architect's role in the intake process:

### Architecture
```
Customer (WhatsApp)
  → Meta WhatsApp Cloud API
    → Webhook (Node.js / Next.js on Vercel)
      → Claude Haiku (interprets text + images + audio)
      → Whisper (transcribes voice notes)
      → Classifies: service type, urgency, city, location
      → Generates structured work order
      → Responds to customer via WhatsApp
      → Dashboard displays all work orders
```

### Capabilities
- **Text understanding**: Interprets maintenance requests in natural Colombian Spanish
- **Image analysis**: Receives photos of problems (leaks, cracks, electrical issues) and describes what it sees
- **Voice note transcription**: Customers often send audio — Whisper transcribes, then Claude interprets
- **Intelligent classification**: Maps each request to service type (from 9 categories), urgency level (4 tiers), and city (25+ locations)
- **Structured output**: Generates formatted work order summaries
- **Interactive confirmation**: Uses WhatsApp buttons for customer confirmation
- **Web dashboard**: Shows all work orders with status, classification, and conversation history

### Technical Details
- **Runtime**: Next.js 14 on Vercel (serverless)
- **AI**: Claude 3 Haiku via REST API (classification + conversation), OpenAI Whisper (audio transcription)
- **Storage**: Redis (work orders, conversation state, message history) with in-memory fallback
- **WhatsApp**: Meta Cloud API (webhooks + send API)
- **Language**: 100% Spanish — prompts, UI, responses all in Colombian Spanish
- **Config-driven**: Business details (services, cities, team) defined in a single config file — designed to be generated by an intake agent for future customers

### Data Model
```typescript
WorkOrder {
  id, createdAt, status
  description, serviceType, urgency, city, location
  customerPhone, customerName
  architectPhone, technicianPhone
  scheduledDate, scheduledTime, accessAuthorized
  estimatedValue, anticipoMaterials, anticipoViaticos, anticipoManoObra
  mediaUrls[], messages[]
}

WorkOrderStatus:
  solicitud → clasificado → arquitecto_notificado → tecnico_asignado
  → fecha_acordada → acceso_solicitado → acceso_autorizado
  → en_ejecucion → terminado → facturado
```

### System Prompt (Core Logic)
The AI agent is instructed to act as Redin's architect in the initial WhatsApp interaction:
- Understands maintenance problems from text, photos, and audio
- Asks focused follow-up questions (max 2 at a time) when info is incomplete
- Classifies service type, urgency, city
- Generates structured work order summaries
- Flags emergencies (floods, electrical shorts, structural risk) as URGENT
- Never invents pricing — defers to technical team for quotes
- Speaks natural Colombian Spanish, professional but warm

## What's Missing (Integration Gap) — The Critical Lesson

The bot works as a standalone WhatsApp agent, but it does NOT yet integrate with Redin's existing AppSheet/Google Sheets system. This means:
- Work orders live in the bot's database, not in their existing system
- The architect still needs to manually transfer data from the bot's dashboard to AppSheet
- It reduces work but doesn't eliminate the manual loop entirely — it just moves the bottleneck

**This is the single most important lesson from this build:** The business already HAS a system. They built it themselves. They know how to use it. They don't want a second system — they want their EXISTING system to work through WhatsApp automatically.

For Redin specifically:
- The owner opens AppSheet every morning and sees his work orders. That's his workflow.
- If the WhatsApp bot writes new work orders directly into the same Google Sheet that powers his AppSheet, he sees them appear in his familiar interface. No learning curve. No "check two places."
- If the bot is a separate dashboard with its own data, it's just ANOTHER thing he has to check — and he'll stop checking it within a week.

**The integration path for Redin**: AppSheet runs on Google Sheets. If the owner shares that Google Sheet with our service account (a simple "Compartir" action he already knows how to do), the bot can read and write directly to it. His AppSheet keeps working exactly the same. The difference is that new maintenance requests now arrive automatically instead of him typing them in manually from WhatsApp.

## Key Insights from This Build

1. **The build itself was fast (~2 hours)** — the friction is NOT in building the bot
2. **The real friction is Meta WhatsApp setup** — the customer couldn't create a Meta app (forgot password, new account rejected)
3. **Screenshots are the universal interface** — the customer couldn't explain his data model but could show his screen
4. **Voice notes are critical** — LATAM customers heavily use audio messages, so transcription is essential
5. **Integration is non-negotiable** — without connecting to the existing system, adoption won't stick
6. **The config file IS the product** — everything customer-specific lives in one file that an AI agent could generate from a conversation
